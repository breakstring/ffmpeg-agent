# 媒体服务首版技术选型

状态：技术选型基线，实施与验收状态见[实施进度](../plans/v1-implementation-progress.md)\
日期：2026-10-13\
适用项目：`ffmpeg-agent`\
依据：[首版设计](media-service-v1.md)；执行拆分见[首版实施计划](../plans/v1-implementation-plan.md)。

## 1. 结论与使用规模

首版使用 Python、FastAPI 和 SQLite，交付为一个 Docker 容器。HTTP API、远程 MCP、调度器、回收器和可配置数量的逻辑 Worker 在同一个应用进程中运行；FFmpeg、ffprobe 和图片处理作为受控子进程执行。数据库是容器私有持久卷中的 SQLite 文件，不部署数据库服务或消息队列。

目标是适用于内部部署、低频使用和少量并发的通用媒体服务，并为远程 Agent 提供可发现、可组合的 MCP 工具。同机优先使用共享卷，跨机使用 HTTP 上传或 HTTP 文件源；配置共享卷后这些 HTTP 入口仍可使用。服务独立定义公共契约，不继承特定调用方的数据库、业务资产模型或 SDK 约束。

“不保留历史”指不建设历史任务库、事件档案或永久媒体库。已接受任务的恢复状态、有效产物、租约和短期幂等记录仍需持久保存，否则无法兑现重启恢复和文件保留承诺。

## 3. 一个容器内如何支持并发

### 3.1 进程与职责

容器使用一个应用进程和容器 init。应用进程内运行 API、一个调度器、一个回收器以及 `worker_concurrency` 个逻辑 Worker。每个 Worker 一次领取一个任务，负责获取输入、按依赖执行步骤及发布结果；不同任务可同时运行媒体子进程。

单个任务内部按拓扑顺序串行执行步骤；失败后继续执行可运行的独立分支。首版不同时并行一个任务的多个步骤。因此全服务同时运行的媒体子进程数量不超过 `worker_concurrency`，不会因 DAG 分支而放大并发。ffprobe 和 Pillow 子进程也占用该预算，不在预算外另开进程池。

`worker_concurrency` 默认 1，首版允许 1～4，修改后重启生效。这里的 Worker 是任务执行槽，不是 Uvicorn 的 `--workers`，也不是独立容器。正式运行禁用 Uvicorn 多进程、自动 reload 和内部热重启。配置校验及单实例锁必须阻止多个应用进程共用同一个状态目录。

### 3.2 资源预算

| 配置 | 首版起始值 | 含义 |
| --- | --- | --- |
| `worker_concurrency` | 1，允许 1～4 | 同时占用的任务槽，覆盖获取、处理、发布全过程 |
| `ffmpeg_threads` | 2 | 为支持线程控制的编解码器设置预算，不代表严格 CPU 上限 |
| `ffmpeg_filter_threads` | 1 | 控制可配置的滤镜线程数 |
| `max_queued_jobs` | 32 | 排队容量；满时返回 `429`，不先接受再丢弃 |
| `progress_flush_interval_seconds` | 2 | 合并进度写入；取消、发布和终态立即持久化 |

实际 CPU、内存、进程数和存储边界由容器限制、媒体参数限制、输出字节监测及磁盘预留共同控制。FFmpeg 参数不能精确限制所有解码器、滤镜和内部线程，不能把“2 个 Worker × 2 个线程”当成严格的 4 核消耗保证。提高并发前需用目标机器与 fixture 实测峰值内存、临时磁盘和 API 响应。

低用量首版采用全局 FIFO 调度与调用方排队/运行配额，不引入优先级队列。获取慢的任务也占槽，这是简化资源模型的明确取舍；后续只有出现可量化的等待问题才分离下载与计算并发。

SQLite 只串行化短暂的状态读写。HTTP 下载、FFmpeg 运行、图片处理、文件复制、校验与响应发送均在事务外执行，所以多个媒体子进程可以同时工作。

大文件复制、摘要计算、同步落盘及删除使用有界线程执行和分块取消检查，避免阻塞唯一的 asyncio 事件循环。取消等待协程不代表后台文件操作已经停止；收尾必须等待已启动的操作实际结束并关闭句柄，确认之前保持相关引用，不提交 `inputs_released=true`，也不回收正在使用的文件。单次阻塞系统调用不能强制中断时，任务保持取消收尾状态，由进程/容器关闭流程处理，不能伪报已停止。

## 4. SQLite 的具体使用边界

### 4.1 持久区域与连接

数据库放在服务私有的本地持久卷，例如容器内 `/var/lib/ffmpeg-agent/state/`；与借用输入卷、对外输出卷分开。业务容器不挂载状态目录。首版不支持 NFS、网络文件系统上的 SQLite，也不允许不同服务实例共享状态目录。

一个应用进程使用一个 aiosqlite 连接，并通过统一数据访问层访问。采用 `journal_mode=DELETE`、`synchronous=FULL`、`foreign_keys=ON` 和有限的 `busy_timeout`。本方案没有独立读连接池，全部数据库操作在应用层串行，首版无需为读写并行引入 WAL。SQLite 的本地应用边界、写事务行为与同步选项见[适用场景](https://www.sqlite.org/whentouse.html)、[事务文档](https://www.sqlite.org/lang_transaction.html)和 [synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous)。

aiosqlite 将单连接操作交给后台线程队列，并不自动使跨多个 await 的业务事务互斥，见[官方说明](https://aiosqlite.omnilib.dev/en/stable/)。必须由应用锁覆盖完整 `BEGIN → 查询/写入/取回结果 → COMMIT/ROLLBACK`，所有读操作也通过同一入口。异常或协程取消时，确认回滚完成、连接退出事务后再释放锁；无法确认时停止服务接受任务并退出，不复用状态未知的连接。

事务只处理数据库数据；禁止持锁等待下载、媒体执行、文件 fsync、目录重命名或网络发送。修改状态使用条件更新及受影响行数检查；执行提交同时核对当前 `attempt_id`。使用参数化 SQL、外键和唯一约束，不依赖只有某个调用路径会遵守的内存约定。

### 4.2 状态范围与迁移

首版只需要以下逻辑数据，具体表和索引在实施 P1 中确定：

- 任务、规范化定义、当前状态、取消意图、期限及步骤结果。
- 执行尝试、输入获取状态、固定下载副本和发布检查点。
- 托管上传文件的所有权、接收/可用/回收状态、字节数、摘要、保留期及上传幂等。
- 产物、集合成员或清单摘要、保留期限和发布/回收状态。
- 任务内部引用、显式读取租约、正在发送的 HTTP 读取引用。
- 调用方作用域内的幂等键、请求摘要和最小响应定位信息。

不增加历史事件流、完成任务报表表或永久执行日志表。用编号 SQL 迁移与 SQLite `user_version` 管理 schema；迁移只在取得单实例锁、API 尚未就绪时执行。需要备份的升级先停写并生成一致性备份；迁移或完整性检查失败时不自动删库重建。首版不引入 Alembic。

### 4.3 短期清理策略

默认产物保留 24 小时；幂等保证窗口为任务终态后至少 24 小时，响应声明实际截止时间。活动任务及其输入/产物引用不能因时间窗口而被删除。幂等记录尚在时，保留足够的任务状态，保证重放返回的 `job_id` 可查询。

任务进入终态后，可先清除不再需要的来源认证信息和详细执行材料；最小任务记录保留到幂等窗口结束、所属产物及其引用全部回收之后。任务被清除后查询返回 `404`；产物尚有有效租约或下游内部引用时，其授权和定位元数据继续保留。下游任务引用产物不再需要时及时释放，不以永久引用代替保留期。

日志只做有限滚动诊断，不承担审计或历史查询契约。SQLite 删除记录后可复用空闲页，文件不一定立即缩小；不在每个任务结束时运行 VACUUM。若需要压缩，在暂停接收任务的维护窗口执行，不影响有效任务和产物的承诺。

## 5. 接受、执行、取消与恢复

### 5.1 接受与执行资格

`POST /v1/jobs` 在一个事务中完成幂等校验、配额检查、任务与步骤写入，以及托管上传文件和输入产物内部引用获取。事务开始后的当前时间用于判定引用资格；事务提交成功后才返回 `202`。相同请求重放返回 `200`，同键不同请求返回 `409`。规范化规则保留数组顺序，填充 schema 默认值，敏感字段参与摘要但不出现在日志或公开结果中。

调度器在短事务内将排队任务绑定到新的尝试和 Worker 槽。数据库是可靠队列；丢失内存通知不会丢失任务，周期扫描补偿即可，不引入 Celery、Redis、RabbitMQ 或外部调度服务。

执行租约和尝试编号用于判断当前提交资格，不作为操作系统进程死亡证明。任何恢复、超时和回收路径都不能只因租约过期就释放借用输入或删除工作文件。

### 5.2 子进程控制

通过 `asyncio.create_subprocess_exec` 传结构化参数，禁用 shell。每次执行使用独立进程组，持续消费 stdout/stderr，限制诊断缓存大小，避免管道堵塞。探测 JSON 和进度输出分别限制体积；敏感路径与来源信息在记录前脱敏。异步子进程 API 见 [Python 文档](https://docs.python.org/3.14/library/asyncio-subprocess.html)。

取消或超时采用进程组 TERM、有限等待、KILL、wait/reap 的顺序。正常退出也核实受管进程组不再持有工作；停止确认、文件关闭完成后，才在事务中提交终态、`inputs_released=true` 和引用释放。协程被取消、PID 文件存在与否或发出信号都不是完成证明。

任务期限包括排队、获取、全部步骤和发布。网络瞬时失败可在剩余总预算内有限重试；确定性媒体错误不自动重试。Pillow 也使用可终止的辅助子进程，不把无法强制停止的线程任务当作取消保障。

### 5.3 故障与重启

应用进程发生不可恢复故障时退出整个容器，由容器运行时重启；不在存活容器中启动第二个应用进程接管旧子进程。正常关闭停止接收任务、终止并回收子进程，再退出；强制容器终止后，由运行时销毁上一轮容器进程。只有确认这一生命周期边界后，启动恢复才可将旧 HTTP 发送者与旧执行者视为已停止。无需 Docker socket 权限。

启动顺序为：取得单实例锁、打开并检查 SQLite、执行迁移、核对工作目录及发布记录、处理取消意图、恢复可安全继续的任务，然后进入就绪。无法确认旧执行者停止时保持不就绪，不仅凭保存的 PID 杀进程或接管任务。

已经完成的步骤和发布的产物是不可变检查点。重启后复用已固定下载副本及已提交输出；只重试没有提交的部分。借用共享输入仍要求调用方保持不变；若恢复需要已丢失的输入或不兼容的执行环境，明确失败。取消意图优先，不能因重启而重新执行被取消任务。

## 6. 文件、发布与访问

### 6.1 区域和路径

输入、私有工作区、私有状态区及对外输出区分别配置。调用方输入借用不复制、不删除；通过 `storage_id` 和相对 key 访问。按目录文件描述符逐级安全打开路径，拒绝符号链接、目录逃逸和非普通文件，并保证媒体引擎实际读取的是被验证的对象，不能“校验一次路径，再交给 FFmpeg 任意重新打开”。Linux 下具体 FD 传递和引擎协议限制在 P0 做可行性原型，P2 完成正式实现与竞态回归。

媒体可能包含其他文件或网络资源引用。首版采用允许的输入格式和协议，禁止播放列表、多资源输入与不必要的网络协议；受控下载结束不表示解码器可以自由访问外部资源。服务整体需要 HTTP 访问，因此仅靠容器有无网络不能替代媒体解析边界。

### 6.2 可恢复发布

每个尝试写入独立私有目录。校验输出、生成清单，必要时复制到输出文件系统的暂存目录；完成文件与目录同步后，在同一文件系统内重命名发布，随后提交数据库 ready 状态和步骤检查点。集合整体发布，不逐个暴露未完成成员。API 在状态提交前不提供访问引用。

持久记录发布意图、预期文件和完整性信息，以处理文件操作与 SQLite 提交之间的崩溃窗口。重启核对后完成安全提交或定向回收；不凭目录存在判定成功。所有文件操作均在数据库事务外，发布资格通过前后短事务核对。已发布内容、成员清单和输出绑定不再替换；部分抽帧集合也不可补写。

输出区只由服务写入，调用方只读挂载。随机 key 不是访问授权；数据库授权、挂载权限和租约共同定义可消费范围。共享卷用户能在文件系统观察暂存条目时也不能消费它们，必须等 API 宣布 ready。

### 6.3 HTTP 获取与读取

aiohttp 客户端不继承环境代理，手动处理有限次重定向，每跳重新校验 scheme、主机、端口和目标 IP。DNS 检查必须绑定实际连接使用的结果，避免检查后再次解析到不同地址；禁止跨源转发认证头。内部文件服务通过明确规则放行，不统一禁止所有私网目标。TLS 校验保持开启。扩展方式见 [aiohttp 客户端](https://docs.aiohttp.org/en/stable/client_advanced.html)与[解析器接口](https://docs.aiohttp.org/en/stable/abc.html#abstract-resolver)。

以 GET 流式获取并计算实际字节数和摘要，不要求签名地址支持 HEAD。关闭自动内容解压或明确拒绝不支持的 Content-Encoding，保证大小和摘要针对实际保存的媒体字节。下载成功后保存固定副本；中断重试从头获取，首版不实现断点续传。

HTTP 输出必须流式发送。Starlette 的文件响应支持 Range，见[官方响应文档](https://starlette.dev/responses/)，但租约保护由本服务额外实现，不能把框架的 BackgroundTask 当成唯一收尾机制。响应包装覆盖打开文件、实际 ASGI send、断连、超时、取消及 finally；先停止发送、关闭文件，再释放内部引用，不在发送过程中持有数据库事务。

首版明确支持单区间 bytes Range，合法多区间请求忽略 Range 并返回完整 `200`，不生成 multipart。实现及测试包括 HEAD、`206`、`416`、ETag、If-Range 和断连；合法多区间的完整响应也受传输预算限制。产物已 retiring 时，有效的显式租约仍允许相应元数据、成员清单和内容读取，新消费者被拒绝。

集合增加独立分页成员接口 `GET /v1/artifacts/{artifact_id}/members`；任务和产物元数据仅返回摘要及清单入口。分页顺序基于不可变清单，逐项结果有稳定索引。

### 6.4 HTTP 上传与托管输入

`POST /v1/files` 以 `application/octet-stream` 接收一个输入，支持独立上传幂等；`POST /v1/jobs/upload` 增量解析 multipart，先校验 `job` JSON，再按命名 part 写入文件并接受任务。二者共用托管文件管理，不直接把上传字节交给 FFmpeg，也不在请求内等待媒体执行。multipart 的 `upload` 占位只在该入口有效，普通任务仍引用 `uploaded_file/file_id`。

统一中间件需区分小 JSON/MCP 请求和文件上传，不能把整个上传请求体读入内存，也不能简单放大 JSON 的 `max_request_bytes`。在读取文件前完成统一 Token 校验；接收过程中按实际字节限制单文件、总请求、并发接收、闲置/总时限和磁盘余量。增量 multipart 解析还限制 part 数量、元数据大小、文件头和边界缓冲，拒绝重复、缺失及未声明的文件 part。

托管文件位于 `work_dir/_uploads`，与每任务/尝试目录隔离。先持久登记接收记录与服务生成的定位信息，再开始创建文件；文件同步并完整提交后才可引用。默认 TTL 从完整上传时起算 24 小时，接受任务原子取得文件引用，覆盖排队、执行和重试。到期或 release 只撤销新引用资格，已有任务不被中断；清理必须等待接收者/文件操作停止、句柄关闭及有效任务引用释放。

未完整上传文件关闭后进入回收；完整文件已提交但请求内任务尚未接受时，按上传 TTL 有界保留，允许同提交键重试复用。上传和任务提交分别幂等；请求内上传使用规范化任务与文件摘要判定重放，不能用每次新生成的 `file_id` 导致重传产生新任务。同键响应丢失、上传中断、提交前后崩溃和回收竞争需要单独验证，启动恢复仅核对登记的所有数据，不扫描或删除业务输入卷。

### 6.5 远程 MCP 与协议边界

使用官方 Python MCP SDK 在现有 ASGI 应用中挂载 Streamable HTTP 入口；SDK 的 ASGI 集成方式见[官方文档](https://py.sdk.modelcontextprotocol.io/run/asgi/)。增量依赖基线为 `mcp==2.1.0` 和 `python-multipart==0.0.22`，具体传递依赖固定在 `uv.lock`；兼容性以 Python 3.14、当前 FastAPI 和真实客户端的协议测试为准。MCP 只负责协议与工具适配，不维护另一套任务状态或执行器。

语义工具按媒体目标组织，通用任务图工具保留复杂组合能力。六个媒体工具均短请求接受异步任务，返回结构化 `job_id`；状态、取消、文件元数据、产物、租约及 release 工具直接调用与 HTTP 相同的领域方法。工具不提供任意引擎参数、不接受客户端本地路径、不在参数中携带服务 Token。

文件字节仍通过 HTTP 上传和下载；MCP 结果只提供文件/产物标识、状态及不含凭据的访问方式。远程客户端须为 MCP 入口和文件 HTTP 请求配置同一 Bearer Token，不能假定客户端会自动给工具结果中的链接附加认证头。只考虑远程 Streamable HTTP，不交付本地 stdio 或桥接。

## 7. 媒体引擎与首批预设

首版采用 Debian 13 维护的 FFmpeg 7.1 系列包，不自行编译追随最新主版本。截至选型查证，[Debian 包页面](https://packages.debian.org/trixie/ffmpeg)提供 7.1 系列构建和 amd64/arm64 包。实际选用补丁版本、编码器和许可证清单由 P0 的镜像验证记录；两个架构分别验收，不从“存在软件包”推断媒体输出等价。

启动必须检测 FFmpeg、ffprobe、Pillow 版本及预设需要的编码器/格式。缺少所需能力时不就绪，不静默降级编码方式。任务冻结操作版本和预设内容，同时记录实际镜像与引擎版本。升级先排空任务，或保留可运行原有冻结定义的兼容实现。

| 操作/预设 | 首版准备固化的行为 |
| --- | --- |
| `media.probe.v1` | 规范化容器和流信息；缺失字段为空，报告 JSON 为产物 |
| `web_720p_v1` | MP4、H.264/libx264、yuv420p；画面等比装入 1280×720、不过度放大、有效偶数尺寸；CFR 30fps、CRF 23、medium、faststart；存在音频时转 AAC 128k/48kHz/双声道 |
| `aac_stereo_128k_v1` | M4A/AAC、128k、48kHz、双声道；用于音频转码及视频音轨提取 |
| `wav_mono_16k_v1` | WAV/PCM s16le、16kHz、单声道；用于音频转码及视频音轨提取 |
| `video.extract_audio.v1` | 首版按上述预设转换所选音轨；不提供任意编码 copy，缺音轨明确失败 |
| `video.extract_frames.v1` | JPEG/PNG 集合；按归一化展示时间选择第一张不早于请求点的可解码帧，记录实际 PTS；保留请求顺序和重复时间点的独立结果 |
| `image.resize.v1` | 静态 JPEG/PNG/WebP；先处理 EXIF 方向，再按 contain/cover 缩放；拒绝动画、多页和超限像素；透明图片转 JPEG 必须按约定背景合成 |

图片使用 Pillow 的 [EXIF 方向处理](https://pillow.readthedocs.io/en/stable/reference/ImageOps.html#PIL.ImageOps.exif_transpose)。输出去除 EXIF/GPS 等无关元数据；首版的颜色空间、ICC 支持范围、透明背景默认值及禁止放大时 cover 的拒绝规则必须在 P0 固化并形成样例。视频的方向、SAR、奇数尺寸、HDR/色彩支持范围以及抽帧时间归一化也必须明确；不支持的组合拒绝，不以成功状态掩盖语义变化。

上述预设是实施基线，尚未实测。版本化预设在完成 P0 验证后冻结，同名预设不得改变意义；需要更改时增加新版本。

## 8. 默认限额、认证与运行维护

以下是低用量部署的起始配置，P7 在目标机器验证后调整。API 公布实际生效值；测试不能把建议值误当成固定协议。

| 项目 | 起始值/规则 |
| --- | --- |
| 单任务输入 / 步骤 / 抽帧点数 | 最多 4 个输入、16 个步骤、100 个抽帧点 |
| 单个输入 / 单任务输出总量 | 各不超过 2 GiB；另限制时长、像素与临时文件总量 |
| 任务总期限 | 3600 秒，含排队；超时后仍需完成停止与释放收尾 |
| HTTP 获取 | 连接 10 秒、读闲置 30 秒、一次获取总预算 300 秒；最多 3 次尝试且受任务剩余预算限制 |
| HTTP 单次输出 | 总预算 600 秒；用 Range 和显式租约完成更长的分段消费 |
| 托管上传保留 | 默认完整上传后 24 小时；到期或 release 后停止新引用，任务引用继续保护 |
| 进程停止 | TERM 后最多等 10 秒，再 KILL 并确认停止 |
| 崩溃恢复 | 每任务最多 2 个执行尝试；有取消意图、确定性错误或已过总期限时不重跑 |
| 产物保留 | 默认 24 小时，可申请延长；从发布时起累计最多 7 天 |
| 显式读取租约 | 默认 15 分钟，单次最长 1 小时，累计最长 24 小时；retiring 后不续期 |
| 幂等保证窗口 | 终态后至少 24 小时，返回实际截止时间 |

认证采用一个可选服务 Token。私有配置中显式设置 `service_token` 为 Token 时，HTTP API、MCP、上传和下载统一校验 Bearer；设为 `null` 时开放访问，内部使用固定 `service_caller` 形成服务空间，仅配置一个调用方时自动选定。省略该字段保持已有 `callers.tokens` 认证兼容；简单模式不增加用户、角色或 OAuth 系统。Token 不进入工具参数、URL、日志或公开结果。跨机经现有 HTTPS 入口访问；来源 URL/认证头按敏感信息受限保存，公开状态、日志和错误不回显。

就绪检查覆盖状态库、挂载权限、最低可用空间、引擎能力及恢复完成状态；存活检查不因单个坏媒体或短暂繁忙而触发重启。日志按 request/job/step/attempt ID 关联，记录排队、获取、处理、发布及回收耗时。首版提供结构化日志与健康接口，不增加 Prometheus/Grafana 等独立依赖。

## 9. 编码前验证与后续扩展条件

实施 P0 先验证 Python/依赖/镜像组合、编解码能力、FD 安全读取、图片方向与关键媒体样例，再开始完整 API 实现。构建固定 uv.lock、系统包版本和基础镜像 digest，并保存可复现的构建信息。uv 的冻结同步行为见[官方文档](https://docs.astral.sh/uv/concepts/projects/sync/)。

首版不实现多进程 API、独立 Worker 容器、分布式租约、PostgreSQL、Redis、Celery、对象存储 SDK、GPU、NFS 或长期历史查询。只有单节点资源持续不足、数据库等待明显影响 API、需要跨节点执行或需要高可用时，再评估拆分。增加容器副本不属于安全扩容方式；扩展必须重新设计任务领取、存储可达性和文件生命周期。

本文记录技术选型与默认预算的基线，不代表版本组合、处理行为或容量已经验收。具体构建、执行结果和部署限制见[实施进度](../plans/v1-implementation-progress.md)，只有实际验证证据才能支持相应交付结论。
